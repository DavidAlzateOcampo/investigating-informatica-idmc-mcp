1️⃣ Business Issue #1: Monitor Taskflows & Identify Runs Ended With Errors

        Tool: get_taskflow_runs
      


      

        

          
How Informatica IDMC Solves This via REST

          

            Informatica provides the Taskflow Status Resource under /active-bpel/services/tf/status
            (note: /saas is omitted on ActiveVOS paths). However, querying it directly returns runs across the entire organization or lacks subtask fault messages unless you make a second call per failed runId.
          

          

            
              

                Step
                Endpoint (`dm-us`)
                Purpose
              

            
            
              

                1
                GET /saas/public/core/v3/objects?q=type=='TASKFLOW'
                Resolves which taskflows belong to IDMC_PROJECT_NAME.
              

              

                2
                GET /active-bpel/services/tf/status?startTime=...&runStatus=FAILED
                Fetches taskflow executions in the time window (`SUCCESS`, `FAILED`, `SUSPENDED`, `RUNNING`).
              

              

                3
                GET /active-bpel/services/tf/status/{runId}
                Automatically invoked by our MCP server for `FAILED`/`SUSPENDED` runs to extract the exact faulted Mapping Task and error code.

2️⃣ Business Issue #2: Discover & Execute Taskflows Within a Project Without Knowing the API Chain

        Tools: list_project_taskflows & execute_project_taskflow
      


      

        

          In standard IDMC usage, running a taskflow requires knowing its published Service URL or internal FRS ID.
          With our MCP server, the user simply asks: "What taskflows exist in my project, and please run tf_Daily_Customer360_Refresh."
          The MCP server executes the 4-step chain invisibly and enforces a strict security boundary so taskflows outside IDMC_PROJECT_NAME raise ProjectAccessDeniedError.
        


        

          
            

              Hidden Step
              Behind-the-Scenes HTTP Call
              What the MCP Server Does Automatically
            

          
          
            

              Step 1
              POST https://dm-us.informaticacloud.com/saas/public/core/v3/login
              Logs in, caches INFA-SESSION-ID, and auto-discovers the `dm-us` pod URL (`https://usw5.dm-us.informaticacloud.com`).
            

            

              Step 2
              GET /saas/public/core/v3/objects?q=type=='TASKFLOW' and location=='Finance_Customer360'
              Verifies that the requested `taskflow_name` exists inside the hardcoded project (`Finance_Customer360`). Blocks cross-project execution!
            

            

              Step 3
              POST https://usw5.dm-us.informaticacloud.com/active-bpel/rt/{taskflow_service_name}
              Invokes the published taskflow REST endpoint with optional JSON input parameters and captures the generated runId.
            

            

              Step 4
              GET https://usw5.dm-us.informaticacloud.com/active-bpel/services/tf/status/{runId}
              Polls initial execution status (`RUNNING` / `SUCCESS`) and returns a clean receipt to the user.
            

          
        

      

    


    
    

      

        
3️⃣ Business Issue #3: Project-Oriented Profiling & CDGC Rule Occurrence Quality Scores

        Tool: get_project_profiling_and_dq_scores
      


      

        

          
Why Chaining CDP + CDGC APIs Is Required

          

            In IDMC, column statistics (null %, distinct %, patterns) live in Cloud Data Profiling (CDP) on
            https://<pod>-dqprofile.dm-us.informaticacloud.com, whereas Data Quality Rule Occurrences
            (pass/fail scores, thresholds, governance dimensions) are stored in CDGC on
            https://idmc-api.dm-us.informaticacloud.com under class com.infa.ccgf.models.governance.RuleInstance.
          

          

            Our MCP tool chains all 4 endpoints automatically while locking `frsProjectName == IDMC_PROJECT_NAME`, so the user never supplies a project parameter.

4️⃣ Business Issue #4: How to Use CLAIRE APIs for Metadata & Root-Cause Insights

        Tool: get_claire_project_insights
      


      

        

          Informatica CLAIRE® surfaces intelligence across three programmable layers in `dm-us`:
          (1) CDGC Enriched Metadata Attributes (`POST /data360/search/v1/assets` with `segments=all`),
          (2) Native CLAIRE Shared MCP Agents in IDMC AI Agent Engineering, and
          (3) Cross-Pipeline Anomaly Correlation in our `get_claire_project_insights` tool.
        


        

          

            
🔍 1. CLAIRE Auto-Classification & Recommendations

            
    
              
  • PII / Sensitivity Tagging (`core.autoClassification`): Detects `National_Tax_Identifier_PII` (99.2% confidence) on `DIM_CUSTOMER.TAX_ID_NUMBER` and `Electronic_Mail_Address_PII` (99.8% confidence) on `EMAIL_ADDRESS`.
    • 
              
  • CLAIRE Cleansing Rule Suggestion: Identifies 1,350 records with legacy `'XX-'` prefix from EMEA CRM batch and recommends rule `std_Strip_Legacy_Country_Prefix`.
    • 
              
  • PK/FK Relationship Discovery: Infers 99.98% join overlap between `FCT_INVOICE_LEDGER.BILL_TO_CUST_ID` and `DIM_CUSTOMER.CUSTOMER_ID`.
    • 
            

          


          

            
⚡ 2. CLAIRE Pipeline Failure ↔ DQ Drift Correlation

            

              By combining ActiveVOS taskflow fault logs with CDGC Rule Occurrence observability (`CLAIRE-ANOM-501`), the MCP server explains why a pipeline failed in business terms:
            

            
"Taskflow 'tf_CrossBorder_Tax_Compliance' (Run 914510835553251089) failed at subtask 'mt_Validate_Customer_TaxID_Format' because Rule Occurrence 'RO_CUST_TAX_ID_VALIDITY' dropped -16.7% (from 99.1% to 82.4%)."

    2.

3 Steps to Build a Self-Managed MCP Server in IDMC via Cloud Application Integration (CAI)

          
    
            
  1. Step 1 — Service Connectors: In Application Integration, create Service Connectors wrapping v3/login, v3/objects, /active-bpel/rt/, and /profiling-service/api/v1/profile.
    2. 
            
  2. Step 2 — CAI Process with Hardcoded Project Variable: Create a CAI Process that sets a constant variable v_Project = "Finance_Customer360", chains the Service Connector actions, and publish it to the Cloud Server.
    3. 
            
  3. Step 3 — Expose in AI Agent Engineering: Go to AI Agent Engineering → MCP Servers → Self-Managed MCP Servers, select your published CAI Process as an MCP tool, and copy the SSE URL into .mcp.json.
